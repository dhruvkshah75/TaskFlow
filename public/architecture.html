04 / Capacity follows the queue

A queue gets deeper.
A fleet gets bigger.

KEDA observes the low priority Redis queue and adjusts the worker deployment between 2 and 20 replicas.

The current manifest polls every 2 seconds, sets a target list length of 5, and configures a 30 second cooldown. Both priority queues are served by the same worker fleet.

05 / When a part stops

Work can fail.
Make it recoverable.

Heartbeats, leader leases, and reconciliation give the system ways to detect interrupted work. Handlers should tolerate being run again.

A worker disappears

Workers publish heartbeats every 3 seconds with a 10 second TTL. The queue manager scans running tasks every 10 seconds and requeues tasks whose worker heartbeat is missing, up to 3 retries.

Inspect heartbeat handling ↗
The queue manager loses leadership

Leadership uses a Redis lease with a 10 second TTL, renewed every 3 seconds. A contender can acquire the lock after the lease expires; the Kubernetes manifest currently runs one queue manager replica.

The queue and database disagree

A reconciliation loop republishes queued tasks every 30 seconds. This can produce duplicate delivery, so task handlers should be idempotent. A separate loop inspects stale entries in the low priority processing list.

A Python handler raises an error

The worker marks the task FAILED and removes its message from the processing list. The dynamic handler wrapper also sets a 180 second timeout. The current worker records task status rather than persisting the handler’s return value.
